## Known divergences and harness reconciliations

1. System-program error rendering. Agave (and the cgo engine) surfaces
   system-program failures as InstructionError Custom(n) (SystemError enum
   codes); mithril's Agave-JSON rendering leaks its internal sentinel names
   instead (e.g. "SystemProgErrResultWithNegativeLamports" where Agave says
   {"Custom":1}), because mithril's agaveInstrErrName only strips the
   InstrErr/TxErr prefixes. The failures are semantically identical, so
   normalizeError folds mithril's SystemProgErr* names onto the Custom codes
   before comparing. Fixing the rendering itself belongs in mithril.

2. InsufficientFundsForRent account_index (RESOLVED). The mithril fork now
   plumbs the offending account's transaction index through
   TransactionError.AccountIndex for rent-state failures, so both engines
   report the same index (1, the recipient, in transfer-rent-shortfall).
   The variant and the index detail are both compared hard.

3. Log framing and ic_msg detail (RESOLVED for the system program). The
   mithril fork emits the Agave per-instruction framing lines (invoke
   [depth] / success / failed: ... / consumed N of M compute units) and now
   also ports every ic_msg detail line of Agave's system program
   (system_processor.rs and system_instruction.rs: Create Account/Allocate
   already-in-use, Allocate too-large, must-sign variants, Transfer
   insufficient/from-must-not-carry-data/seed-mismatch, and the
   Advance/Withdraw/Initialize/Authorize nonce messages), byte-exact
   including the Rust derived-Debug rendering of the Address struct
   ("Address { address: X, base: None }"). The full log arrays of
   transfer-ok, memo, failed-instruction-logs and
   create-account-already-in-use are all compared hard. Residual: ic_msg
   lines of OTHER native programs (vote, the bpf loaders, stake, ...) are
   not ported by the pure pipeline; scenarios exercising those failure
   paths would need their full log arrays kept soft.

4. SetAccount on the RecentBlockhashes sysvar address. Both engines refresh
   the typed sysvar cache (programs observe the written data), but neither
   rebuilds its internal blockhash bookkeeping: Rust keys transaction age on
   its internal latest_blockhash, while the pure engine's age validation
   reads the sysvar queue, so overwriting RecentBlockhashes can affect age
   checks only on the pure engine (documented in mithrilsvm sysvars.go).

5. Blockhash-check-off execution. Rust simply skips the age check; the pure
   engine instead temporarily injects the tx blockhash into the
   RecentBlockhashes cache for the duration of the replay call (mithril has
   no skip-age-check switch), so a program reading the sysvar mid-tx sees an
   extra entry only on the pure engine (documented in mithrilsvm tx.go).

6. Delay visibility of tx-deployed programs. The pure engine executes at
   slot s+1 so that AddProgram-installed programs are immediately usable
   (Rust forces effective_slot = current_slot in its program cache); as a
   side effect a program deployed via a real bpf-loader transaction at clock
   slot N is invokable at slot N on the pure engine but requires warping
   past N on the cgo engine (documented in mithrilsvm tx.go newSlotCtx).
